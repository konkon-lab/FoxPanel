# 组件进程

组件的主进程代码(清单的 `main` 入口)跑在组件进程里。这篇讲组件进程怎么分、怎么加载和重载组件、崩溃后怎么办，和核心之间传哪些消息，以及核心替组件做的几件事：分发输出、听写、翻译，推应用信息，在提供方和使用方之间转远程服务的状态和调用，替显示方开面板页面、把页面的帧交给它。组件能用的接口见 [SDK](sdk.md)。

## 源码

| 文件 | 内容 |
|---|---|
| `src/component-host/main.ts` | 组件进程的入口：Cordis 根上下文、给组件的服务、加载和卸载 |
| `src/component-host/owned.ts` | 一个组件占用的东西(监听、登记、面板页面)：卸载时逐个放掉 |
| `src/component-host/handles.ts` | 关掉核心复制进本进程、没有组件收的 NT 句柄 |
| `src/main/components/host.ts` | `ComponentHost`：核心这边管一个组件进程，启动、重启、收发消息 |
| `src/main/components/hosts.ts` | `ComponentHosts`：把几个组件进程合起来用 |
| `src/shared/host-protocol.ts` | 核心和组件进程之间的消息 |
| `src/shared/component-services.ts` | 各运行环境共用的总线、组件数据接口和 `ctx.relay` 的外形(`relayOver`) |
| `src/main/relay.ts` | `ServiceRelay`：远程服务的通道 |
| `src/main/app.ts` | `AppBridge`：应用信息和主进程组件的通用请求 |
| `src/main/panels.ts` | `PanelPages`：面板页面(按面板 id 持有页面、交帧、保留期) |
| `src/main/panel-window.ts` | 面板窗口和句柄复制的适配(BrowserWindow、kernel32) |

## 进程

组件进程是 Electron 的 `utilityProcess`，入口是 `dist/component-host.js`，有完整的 Node 权限。

| 进程 | 跑哪些组件 | 任务管理器里的名字 |
|---|---|---|
| 共用进程 | 清单没写 `process` 的全部主进程组件 | `FoxPanel 组件` |
| 独立进程 | 清单写了 `"process": "own"` 的组件，每个一个 | `FoxPanel <组件 id>` |

- 预装组件里输入法(`yanuo.ime`)和 SteamVR(`yanuo.steamvr`)是独立进程。
- 一个进程没有要跑的组件时不启动；跑着的进程里组件全停用了就停掉。
- 独立进程的组件停用或卸载时，它的进程停掉。
- Cordis 的服务只在同一个进程里能 `inject`。跨进程的往来走远程服务(`ctx.relay`)、核心的登记表(输出、听写、翻译)，或同一个组件自己的总线频道。
- 进程的标准输出记成运行日志的 `info` 行，标准错误记成 `warn` 行，前面带 `component host:`。

## 加载组件

核心给进程的每个组件是一条 `HostComponent`：

| 字段 | 内容 |
|---|---|
| `id` | 组件 id |
| `file` | `main` 入口的绝对路径 |
| `mtime` | 入口文件的修改时间(毫秒)，读不到时为 0 |
| `config` | 设置：已补默认值，含解密后的 secret 和 `requires` 的服务组件的设置 |

哪些组件在列表里、`config` 怎么合成，见 [组件管理](component-manager.md) 的「开着的组件」。

进程启动后收到 `load`：记下应用信息、面板目录、数据文件夹、程序目录，登记共享模块，然后按列表顺序逐个加载。加载一个组件(`load`)：

1. 从根上下文分出这个组件的上下文，挂上它自己的服务(见下表)。
2. `import()` 入口文件，地址后面带 `?t=<mtime>`：入口文件变了地址就不同，拿到的是新代码。
3. 入口的默认导出当作 Cordis 插件，用 `ctx.plugin(插件, config)` 装上。
4. 回 `loaded`。没有默认导出、`import` 或插件出错时带上错误：这个组件在组件页显示加载失败，别的组件不受影响。

插件在等 `inject` 里的服务时不等它：服务有了它自己起来，后面的组件照常加载(插件的 `apply` 是异步的并且一直不结束时，才会挡住后面的)。加载 5 秒后还在等的，每个等着的服务往运行日志记一行 warn：`waiting for service: <服务名>`，来源是这个组件；这期间服务有了或组件卸载了就不记。

共享模块：组件 `import` 的 `cordis`、`koffi` 由进程里的模块解析钩子指向程序自带的那一份(`cordis` 和页面用的是同一个文件)。组件装在数据文件夹里，靠这个钩子找到它们。

根上下文上没有共用的服务。每个组件自己的服务：

| 服务 | 内容 | 组件卸载时 |
|---|---|---|
| `id`、`config`、`dataDir`、`appDir` | 组件 id、设置、数据文件夹、程序目录 | |
| `log` | 写一行运行日志，来源是组件 id | |
| `storage` | 组件数据，每次读写发消息给核心 | |
| `bus` | 总线 | 取消它登记的全部监听 |
| `output`、`input`、`translator` | 登记输出、听写、翻译 | 去掉登记 |
| `status` | 上报状态栏的一项 | 去掉这一项 |
| `logs` | 收运行日志的每一行 | 取消监听 |
| `relay` | 远程服务：用别的组件提供的、登记成提供方 | 取消它的状态回调，退订(本进程没有别的组件在用时)，撤掉它的登记 |
| `app` | 应用信息、开关输出组件、系统剪贴板 | 取消它的回调 |
| `panels` | 面板目录；开面板页面(只有生效的显示方开得了) | 取消它的回调；放开它开的页面(页面留在核心那里一段时间) |

各服务的用法见 [SDK](sdk.md)。

## 重载

组件列表有变化时核心给跑着的进程发 `apply`，进程只动变了的组件(`sync`)：

1. 每个组件的整条 `HostComponent` 转成 JSON 当作签名。设置变了(含 secret、服务组件的设置)、入口文件的修改时间变了，签名就变。
2. 已加载的组件里，新列表中没有的、签名变了的，逐个卸载：停掉它的插件，把它占着的东西按登记的相反顺序放掉。
3. 新列表里还没加载的(新增的和刚卸载的)按列表顺序加载。
4. 把登记的输出、听写、翻译重新告诉核心。

签名没变的组件不动。几次 `apply` 一个接一个做，不会交叉。依赖某个服务的组件由 Cordis 跟着服务一起停和起。

- 只看入口文件的修改时间：入口没变、只有它引用的别的文件变了时，这个组件不重载。
- 组件在同一个进程里会被卸载后重新加载，停用时要放掉自己开的原生资源。要跨这一次重新加载留着的状态可以放在模块的变量里(入口文件没变时模块还是同一份)：预装的 SteamVR 组件这样留着内存里的布局，改了它的设置以后面板不用再按一次总开关键。
- 核心这边组件列表没变化时不发消息。

## 崩溃和重启

| 常量 | 值 | 含义 |
|---|---|---|
| `RESTART_MS` | 1000 毫秒 | 进程意外退出后等这么久重启 |
| `CRASH_WINDOW_MS` | 60 000 毫秒 | 连续崩溃按这段时间里的退出次数算 |
| `CRASH_MAX` | 3 | 这段时间里退出满这么多次就停下 |

进程的状态(`HostStatus`)：

| 状态 | 含义 |
|---|---|
| `idle` | 没有要跑的组件，进程没启动 |
| `running` | 在跑 |
| `restarting` | 意外退出，等着重启 |
| `crashed` | 连续崩溃，已停下，等手动重启 |

- 进程停掉或意外退出时：它登记的输出、听写、翻译、状态栏项清掉；等着它回话的翻译按失败处理(发送用原文)；它提供的远程服务撤掉(状态变 `null` 并通知订阅方，等它回结果的调用按失败回，排在后面登记过的同名提供者接上)，它的订阅清掉；它收帧的面板页面停画并保留 120 秒(见「面板页面」)。
- 进程没在跑(等着重启、连续崩溃停下)时，核心发给它的消息直接丢掉，不排队也不补发：这段时间里的发送、「正在输入」、清除和总线消息，它里面的组件都收不到。进程重新启动时从 `load` 拿到当时的应用信息和面板目录，内存里已有的日志行也发一遍；组件重新 `ctx.relay.use` 时核心补发当时的状态。
- 停在 `crashed` 的进程由 `components:host-restart` 重新启动(组件页上的按钮)；它的组件列表有变化时也会重新启动，并重新计数。
- 进程里没被接住的异常记一行错误日志(`component host crashed: …`)后进程退出，按上面的规则重启。
- 组件的回调抛出的异常只记一行错误日志，进程不退出。`send`、`typing`、`clear`、听写的 `start` / `stop`、卸载时的清理出错时，日志的来源是那个组件，返回的 Promise 失败也一样记；应用信息的回调、远程服务的状态回调、不等结果的远程调用出错时，来源也是那个组件(不等结果的调用出错，同一个组件的同一个服务 10 秒记一行)；面板目录的回调、面板页面的帧、大小、状态回调出错时，来源是登记它的组件；总线监听、日志监听出错时，来源是宿主(空)，其中总线监听只接同步抛出的异常。
- 几个进程的状态合成一个给主窗口：有 `crashed` 的算 `crashed`，其次 `restarting`、`running`、`idle`。
- 面板页面和主窗口不在组件进程里，组件进程崩了页面还在；显示方的进程崩了，它显示的面板停画，页面里的状态留着。

## 消息

核心和组件进程之间用 `postMessage` 传消息，每条有一个 `t` 字段。带 `req` 的是请求，对方用同一个 `req` 回话。

核心 → 组件进程(`ToProcess`)：

| `t` | 内容 |
|---|---|
| `load` | 进程启动后的第一条：组件列表、应用信息、面板目录、共享模块表、数据文件夹、程序目录 |
| `apply` | 新的组件列表 |
| `info` | 新的应用信息，见「应用信息和通用请求」 |
| `send` | 发送的一句(`text` 原文、`spoken` 译文、`notify` 提示音)和收这一句的输出组件 id |
| `typing` | 「正在输入」开或关，发给有 `typing` 的输出 |
| `clear` | 清除，发给有 `clear` 的输出 |
| `dictate` | 开或关听写 |
| `translate` | 要翻译的文字(带 `req`) |
| `bus` | 别处发来的总线消息 |
| `reply` | 对进程请求的回话：`value`；失败时带 `error`(有这个字段就算失败，文字可以是空的) |
| `logs` | 运行日志的行；进程启动时把内存里已有的行发一遍 |
| `rvState`、`rvActive`、`rvInvoke` | 订阅了的远程服务的状态、本进程里一个登记生效没有、交给本进程里提供方的一次调用，见「远程服务」 |
| `pnList` | 新的面板目录 |
| `pnFrame`、`pnDrop`、`pnSize`、`pnState` | 面板页面的一帧、核心放掉了的一帧、纹理大小、页面的状态，都带 `component`(本进程里开这一页的组件)和 `id`(面板 id)，见「面板页面」 |

组件进程 → 核心(`FromProcess`)：

| `t` | 内容 |
|---|---|
| `loaded` | 一个组件加载完了；失败时带 `error` |
| `outputs` | 进程里登记的输出(`id`、`live`、`typing`)、接了听写的输入源 id(按组件顺序)、有没有翻译 |
| `storage` | 组件数据的一次读写(带 `req`) |
| `bus` | 组件发的总线消息 |
| `log` | 一行运行日志：组件 id、文字、级别 |
| `status` | 组件上报的状态栏项，`null` = 去掉 |
| `translated` | 翻译的结果：译文，或 `error` |
| `outSend`、`outTyping`、`outClear`、`inDictate`、`trAsk`、`setOn`、`clipRead`、`clipWrite` | 组件要核心做的事(`AppRequest`)，见「应用信息和通用请求」 |
| `rvServe`、`rvClose`、`rvState`、`rvUse`、`rvCall`、`rvResult` | 远程服务(`RelayRequest`)，见「远程服务」 |
| `pnOpen`、`pnClose`、`pnRelease`、`pnInput`、`pnPaint`、`pnFps` | 显示方对面板页面的操作(`PanelRequest`)，都带 `component`(发消息的组件)和 `id`(面板 id)，见「面板页面」 |

## 输出、听写、翻译

组件用 `ctx.output.register`、`ctx.input.register`、`ctx.translator.register` 登记，进程每次有变化都发一条 `outputs` 给核心。核心把各进程登记的合在一起用(`ComponentHosts`)。任何主进程组件都能让登记了的去做：`ctx.output.send` / `typing` / `clear`、`ctx.input.dictate`、`ctx.translator.translate`(预装的输入法组件发送、开听写、翻译走的就是它们)，消息见下一节。

| 功能 | 规则 |
|---|---|
| 发送 | 发给类别是 `output`、开着、并且登记了输出的组件；每个组件一个输出，后登记的顶掉先登记的 |
| 实时内容(自动送出、PIN) | 只发给登记时写了 `live: true` 的输出 |
| 「正在输入」 | 开着的输出里有带 `typing` 的才发，各进程里带 `typing` 的输出都收到 |
| 清除 | 发给全部进程，带 `clear` 的输出都收到 |
| 听写 | 开始时交给登记了听写的输入源里组件顺序最前的一个(跨进程也按组件顺序)；停止时交给开始的那一个。没有输入源登记时不开 |
| 翻译 | 交给登记了翻译函数的进程。没有翻译时原样返回；翻译函数出错按失败回；等 15 秒(`TRANSLATE_MS`)没有结果算超时 |

组件页每一行的「正在提供的功能」取自这里实际登记了什么。

## 应用信息和通用请求

核心把它知道的情况合成一份 `AppInfo`(`AppBridge`)，随 `load` 给每个新起的进程，之后内容变了(组件的装卸、开关、顺序，输出和听写的登记，界面语言)用 `info` 推给全部组件进程，内容没变不推。组件从 `ctx.app.info` 读，`ctx.app.watch` 收变化。

| 字段 | 内容 |
|---|---|
| `version` | 程序版本 |
| `packaged` | 是安装包里的程序；从源码启动时为假 |
| `locale` | 界面语言 |
| `components` | 装着的全部组件，按组件顺序：`id`、`kind`、`name`、`dir`(文件夹)、`manifest`(清单)、`on`(开关开着)、`active`(在用) |
| `outputs` | 装着的输出组件，按顺序：`id`、`name`、`on`、`live`(收不收实时内容)、`typing`(能不能显示「正在输入」) |
| `inputs` | 接了听写的输入源组件 id，按组件顺序 |
| `canDictate` | 有输入源接了听写 |

组件要核心做的事(`AppRequest`)，带 `req` 的核心用 `reply` 回：

| 消息 | 组件调的 | 核心做什么 |
|---|---|---|
| `outSend` | `ctx.output.send(payload, live)` | 按上一节的规则发给在用的输出，回收到的组件 id；`payload` 的 `text`、`spoken` 不是字符串时回失败 |
| `outTyping`、`outClear` | `ctx.output.typing(on)`、`clear()` | 按上一节的规则转给各进程 |
| `inDictate` | `ctx.input.dictate(on)` | 按上一节的规则开、关听写 |
| `trAsk` | `ctx.translator.translate(text)` | 翻译，回译文；失败回错误 |
| `setOn` | `ctx.app.setOn(id, on)` | 开关一个组件(和组件页的开关是同一个改动)；只对装着的输出组件生效，别的 id 不处理 |
| `clipRead`、`clipWrite` | `ctx.app.clipboard.read()`、`write(text)` | 读、写系统剪贴板；读不了时回空字符串 |

## 远程服务

远程服务是跨运行环境用的服务(`ServiceRelay`)：提供方是一个主进程组件，它发布一份状态、接收调用；使用方在别的组件进程或页面里读状态、发调用。核心不看状态和参数的内容，只管哪个提供方生效、谁订阅了、调用是谁发的。预装的输入法组件用它提供 `keyboard`(见 [输入法](input-method.md))，显示方用它提供 `panels`(见 [SDK](sdk.md#显示方ctxpanels-和远程服务-panels))。

组件进程 → 核心(`component` 是发这条消息的组件 id，核心核对它在这个进程里)：

| 消息 | 组件调的 | 核心做什么 |
|---|---|---|
| `rvServe` | `ctx.relay.serve(name, impl)` | 登记成 `name` 的提供方。组件要在用、清单 `provides` 里有 `name`、就在发消息的进程里，否则不登记并记一行警告(来源是那个组件) |
| `rvClose` | 把手的 `close()`，组件卸载 | 撤掉登记 |
| `rvState` | 把手的 `publish(state)` | 记下这份状态；它是生效的提供方时发给订阅方 |
| `rvUse` | `ctx.relay.use(name)`(本进程第一个用它的组件)，最后一个不用了 | 订阅 / 退订；订阅时马上回一条 `rvState`，带当前的状态 |
| `rvCall` | `remote.call(…)`(带 `req`)、`remote.tell(…)`(不带) | 交给生效的提供方：发 `rvInvoke`，带上调用者 |
| `rvResult` | 提供方的方法返回或出错 | 带 `req` 的调用的结果：转回给发起方(进程用 `reply`，页面是 `relay:call` 的返回值) |

核心 → 组件进程：`rvState`(订阅了的名字的状态，`null` = 没有生效的提供方或它还没发布过)、`rvActive`(`name`、`component`、`on`：本进程里 `component` 对 `name` 的登记生效没有)、`rvInvoke`(一次调用：`name`、本进程里的提供方 `component`、`method`、`args`、`caller`，等结果的带 `req`)。

哪个提供方生效：

- 同名的提供者(在用、`provides` 里有这个名字的组件)里组件顺序最前的那个。它登记了才有提供方；它还没登记时，排在后面的不顶上。
- 排在后面的照样可以登记(记一行警告，写明这个名字由谁提供)，排最前的停了、关了、顺序换了之后由核心让它接上；换了提供方时，等前一个回结果的调用按失败回，状态变了就发给订阅方。
- 提供方所在的进程停了或退出时，它的登记和订阅都清掉。
- 核心把每个登记生效没有告诉提供方(`rvActive`)：登记时发一次(同一个组件没撤就再登记也再发一次)，之后和上次告诉它的不一样时才发；只发给登记所在的那个进程，不发给订阅方。一次变化里变成等着的排在变成生效的前面发。组件开关、顺序变化、登记和撤掉都会重新认一遍。组件进程一侧记在把手上：`active` 在核心告诉之前、撤掉之后是假，值变了才叫 `watch` 的回调。

调用：

- 调用者 `Caller` 由核心填：`{ component, where }`。主进程组件发的 `where` 是 `'process'`、`component` 是核对过的组件 id；面板页面发的 `where` 是 `'panel'`、`component` 是面板 id；媒体页面发的 `where` 是 `'media'`、`component` 是空串。提供方的方法第一个参数就是它。面板页面请显示方收起自己(`ctx.panel.hide()`)时，核心替它往 `panels` 发一个不等结果的 `open(面板 id, false)`，调用者是这块面板。
- 实现是一个普通对象，方法是它自己的属性(原型上的不算)。消息到了就调；带 `req` 的把返回值(是 Promise 时等它)或错误回给核心，错误没有文字时回「出错」；不带的出错只记日志(来源是提供方，同一个组件的同一个服务 10 秒一行)。
- 等结果的调用(`call`)在这些时候失败：方法名或参数不合格、没有生效的提供方、提供方没有这个方法或出错、提供方停了、15 秒(`CALL_MS`)没回。
- 不等结果的调用(`tell`)交给核心就完：同一个组件进程或页面发的按发出的先后送到提供方，交不出去(没有提供方、不合格)时丢掉。
- 方法名只收字母、数字、下划线、`$` 组成、不以数字开头、最长 64 个字符的。参数只收普通数据：普通对象、数组、基本类型、BigInt、二进制缓冲和它的视图；里面有 Map、Set、Error 之类的对象或循环引用时不转。参数存成 JSON 不超过 64 KB(`ARGS_MAX`，二进制按字节数算)。不合格的调用记一行警告，同一个调用方同一个原因 10 秒一行。

页面一侧(IPC `relay:use`、`relay:call`，状态经 `relay:event` 送到页面)：只有面板页面和媒体页面能调，服务名要在这一页的组件清单 `requires`、`uses` 里(见 [总体结构](architecture.md#安全边界))；页面只能用，不能提供。订阅时核心马上把当前状态发给它；页面关了、或它的计划换成够不着这个名字的之后，核心不再给它发。

## 总线、组件数据、日志、状态栏

- **总线**：`ctx.bus.send` 先送给本进程里的监听，同时发给核心；核心转给其他组件进程、主窗口，和登记了这个频道的面板页面、媒体页面。页面发的消息由核心转给全部组件进程和别的页面；媒体页面和面板页面发的、登记收的频道都要以这一页加载的某个组件 id 加 `/` 开头(登记另外放行 `core/`)，否则核心不处理并记一行警告日志，主窗口和组件进程发的不限。页面发的消息里频道名超过 200 个字符的、`core/` 的、数据不是普通数据或存成 JSON 超过 256 KB 的不转发。一个监听抛出异常不影响别的监听。
- **组件数据**：`ctx.storage` 的每次读写是一条 `storage` 请求，核心读写文件后回 `reply`。文件和限制见 [组件管理](component-manager.md) 的「组件数据」。
- **日志**：`ctx.log` 发 `log`，核心记进运行日志。核心把新的日志行发给全部组件进程，进程里留最近 2000 行，`ctx.logs.on` 登记的监听先收到已有的行。见 [运行日志](logs.md)。
- **状态栏**：`ctx.status.set` 发 `status`，核心按格式检查后记下，每个组件一项，格式不对的当作去掉。状态栏的显示见 [主窗口](main-window.md)。

## 面板页面

面板页面由核心持有(`PanelPages`，`src/main/panels.ts`)：按面板 id 一块面板一页，显示方来开，核心把页面的帧交给它。离屏渲染、复制句柄只能在 Electron 主进程里做，核心把它们做成给显示方的接口 `ctx.panels`(成员见 [SDK](sdk.md#显示方ctxpanels-和远程服务-panels))。页面本身见 [面板页面](panel-page.md)，预装的显示方见 [SteamVR 悬浮面板](steamvr.md)。

**面板目录**：在用的组件声明的全部面板(`PanelInfo`)，按组件顺序。随 `load` 给每个新起的进程，变了用 `pnList` 推给全部组件进程；组件从 `ctx.panels.list` 读、`ctx.panels.watch` 收变化。页面出过错的面板(加载失败、页面的进程退出)连同原因显示在组件页这个组件上。

显示方 → 核心(`PanelRequest`，都带发消息的组件 `component` 和面板 `id`)：

| 消息 | 组件调的 | 核心做什么 |
|---|---|---|
| `pnOpen { mode }` | `ctx.panels.open(id, mode)` | 开这块面板的页面，把发起的组件记成收帧方，见下面「开页面」 |
| `pnClose { linger }` | 把手的 `close()`(`linger: false`)；组件卸载(`linger: true`) | 不保留：放掉没还的帧，销毁页面。保留：页面停画，进保留期 |
| `pnRelease { seq }` | `feed.release(seq)` | 放掉这一帧的纹理 |
| `pnInput { event }` | `feed.input(event)` | 指点事件收窄后换成页面的鼠标事件(坐标从纹理像素换成页面像素)：移动(带不带左键)、按下、松开、滚轮、移出 |
| `pnPaint { on }` | `feed.setPainting(on)` | 停画：页面不出帧，放开后台节流；恢复：接着画并重画一帧。窗口方式下是隐藏 / 显示窗口。页面自己得到通知(`ctx.panel.visible`) |
| `pnFps { fps }` | `feed.setFrameRate(fps)` | 改帧率，夹在 1 和清单的帧率上限之间；窗口方式下不管 |

`pnOpen` 以外的消息只认这一页当前的收帧方(那个进程里的那个组件)发的，别的进程、同一个进程里别的组件发的都不算。

核心 → 显示方(都带收帧的组件 `component` 和面板 `id`)：

| 消息 | 内容 |
|---|---|
| `pnFrame { seq, handle, width, height }` | 一帧：`handle` 是复制进这个进程的 NT 句柄(十进制字符串)，宽高是这一帧纹理的实际像素 |
| `pnDrop { seq }` | 核心放掉了这一帧(压着的帧太多)，不能再用 |
| `pnSize { width, height }` | 面板的纹理像素：页面像素 × 纹理倍数，取整(窗口方式下是页面像素)。帧的宽高可能比它多几个像素，以帧为准 |
| `pnState { state, detail? }` | 页面的状态：`loading`、`ready`、`failed`、`gone` |

**开页面**：

- 发起的组件要是当前生效的显示方(远程服务 `panels` 的提供者里组件顺序最前的在用的那个)、并且就在发消息的进程里，否则回 `failed`(`not the active display`)并记一行警告。面板不在目录里回 `failed`(`no such panel`)；同时存在的页面已经有 12 个(`PANEL_PAGES_MAX`，保留期里的也算)回 `failed`(`too many panels`)；窗口建不出来回 `failed`(`cannot open the page`)。
- 没有这一页时建窗口(`src/main/panel-window.ts`)：离屏方式是隐藏、无边框、透明的离屏窗口(`useSharedTexture`，`deviceScaleFactor` 是清单的纹理倍数，帧率是清单的上限)，窗口方式是不能改大小的普通窗口(标题是面板的名字)；清单没写 `sound` 的静音。窗口建好、加载地址之前登记为这块面板的页面(带上计划里的组件 id 和远程服务名)，然后加载 `fox://<面板 id>.panel/panel.html`。
- 页面已经在、显示方式相同：接过来——放掉交给前一个收帧方的帧，前一个不是它时告诉前一个 `gone`(`taken over`)，把大小和状态发给新的，开始画并重画一帧。页面里的东西原样留着。
- 页面已经在但显示方式不同(离屏 ↔ 窗口)、或页面出过错：销毁重建。

**每一帧**(离屏方式)：

| 步骤 | 做什么 |
|---|---|
| 交帧 | 页面画出的一帧是 GPU 共享纹理。有收帧方且在画时，核心用 `DuplicateHandle` 把纹理的 NT 句柄复制进收帧的进程(那个进程的进程句柄只申请 `PROCESS_DUP_HANDLE` 权限，每个进程打开一次，进程退出时关)，发 `pnFrame` |
| 用完 | 显示方用自己的 D3D 设备打开句柄、复制内容，然后自己关掉句柄并回 `pnRelease`；核心收到后放掉这一帧的纹理 |
| 压帧 | 核心替一页最多压着 4 帧(`HELD_MAX`)，再来一帧时放掉最早的并发 `pnDrop`，页面才有纹理可画 |
| 不交的帧 | 没有收帧方、停着画、句柄复制不了、纹理不是页面本身的那一层(原生弹出层)时，这一帧直接放掉。窗口已经销毁或换掉之后迟到的帧也放掉 |
| 没人收的帧 | 组件没登记帧回调、或页面已经关了而帧还在路上时，组件进程自己关掉复制进来的句柄(`src/component-host/handles.ts`)，关完(或关不掉)之后回 `pnRelease`；关不掉时记一行错误日志，同一个错误只记一次 |

**页面的寿命**：

- 保留期：收帧的进程停了或退出、显示方的组件卸载(`pnClose` 带 `linger`)时，页面放掉帧、停画，保留 120 秒(`LINGER_MS`)。期间生效的显示方再来开，接回原页面：不重新加载，页面里没发出去的内容都还在。到期没人接就销毁。别的组件进程退出不影响它。
- 组件变了(`sync`)：面板不在目录里了，页面销毁，收帧方得到 `gone`(`removed`)；这一页的计划变了，只重载这一页(状态回到 `loading`，加载完回 `ready`)；页面尺寸变了改窗口大小并发 `pnSize`；帧率上限变了跟着设；纹理倍数或出不出声变了重建窗口，收帧方和画不画照旧(在保留期里的只销毁，再来开时按新的建)。
- 页面加载失败、页面的进程退出：状态变 `failed`(`detail` 是原因)，记一行错误日志，原因记在这块面板上(组件页显示)；显示方再开时重建。
- 窗口被关掉(窗口方式下用户关的)：页面拿掉，收帧方得到 `gone`(`closed`)。
- 多个屏幕缩放比例不同时系统会改隐藏窗口的大小。核心发现离屏页面的大小和登记的相差超过 4 像素就改回去，同一页只记一次警告日志。窗口建好时内容区会和要的差出来——比桌面大的被系统夹小，屏幕缩放不是整数倍时普通窗口差一两个像素(125% 时 480 × 200 的页面建出来是 482 × 199)——核心在加载之前按页面尺寸再设一次，离屏窗口和普通窗口都设。
- 离屏页面的尺寸对齐(`fit`)：屏幕缩放不是整数倍(比如 1.75)时，窗口的大小按屏幕像素取整、换回页面像素时又往上取整，画出的帧会比登记的页面尺寸多 1 像素(1400 × 490 画成 1401 × 491)。核心看到帧的大小(帧的像素 ÷ 纹理倍数)和登记的差几个像素时，把窗口设小或设大这么多，之后画出的正好是登记的尺寸。同一个大小的帧只比对一次，一页最多改 2 次，差超过 4 像素的不归这里；所以每块离屏面板开头会有一帧多 1 像素的，显示方按帧的实际宽高重建一次纹理。被系统改了大小时改回的是对齐后的大小。窗口方式不比对。

显示方的进程里可以开着好几块面板的页面；哪些面板开页面、什么时候停画和关掉由显示方按自己的布局定(预装的 SteamVR 组件见 [SteamVR 悬浮面板](steamvr.md#面板表照布局对一遍))。

组件进程一侧(`src/component-host/main.ts`)：页面按「开它的组件、面板 id」记，核心发来的四种消息按这两项找到把手。显示方等着时(把手的 `active` 为假)不开页面，所以平时不会被拒绝。同一个进程里两个组件开同一块面板各记各的：不是生效显示方的那个得到 `failed`，它关掉自己的把手不影响另一个组件的页面。
